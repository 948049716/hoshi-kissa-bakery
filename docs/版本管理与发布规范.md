# 《一起做猫饼》版本管理与发布规范

> **适用范围**：客户端（`05-微信小游戏版本/`）、云函数（`05-微信小游戏版本/cloudfunctions/kissa_sync/`）、CI/CD 构建脚本（`scripts/` & `.github/workflows/`）以及全仓策划技术文档（`docs/`）。
> **实施约束**：`v0.9.0` 代码落地时同步对齐 `constants.js`、`upload_minigame.mjs` 与 `minigame-ci.yml`。

---

## 一、版本号格式与生命周期阶段

全项目遵循 **语义化版本 2.0.0（SemVer：`MAJOR.MINOR.PATCH`）**，并以 **是否已在微信公众平台正式面向公众过审发布** 作为 `0.x.y` 与 `1.0.0` 的唯一分水岭：

| 版本号格式 | 生命周期阶段 | 适用场景与升降级规则 |
| :--- | :--- | :--- |
| **`0.x.y`** | **上线前研发 / 内测期** | 尚未向公众正式发布前的所有版本：<br>• **`0.1.0 ~ 0.4.0`**：早期物理玻璃罐原型探索期（已淘汰并归档至 `docs/archive/`）<br>• **`0.8.0`**：异形 2048 + 3 席出餐 + 30 关重构基线（现行代码）<br>• **`0.9.0`**：内测经济平衡与厨具机制精修版（Beta Overhaul）<br>• **`0.9.1 ~ 0.9.x`**：提审前真机兼容、引导与数值微调（仅升 `PATCH`） |
| **`1.0.0`** | **微信小游戏正式首发版** | 首次提交微信公众平台审核并面向公众正式发布上线时锁定为 **`1.0.0`**。 |
| **`1.x.y`** | **上线后长线迭代期** | 正式上线后的版本演进：<br>• **`MINOR` (`x`) +1**：新增主线章节（如第 4~5 章）、新玩法模式、新动物顾客/搭档/核心系统（如 `1.1.0`、`1.2.0`）<br>• **`PATCH` (`y`) +1**：线上 Bug 修复、单关目标分微调、素材热修（如 `1.0.1`）<br>• **`MAJOR` (`2.0.0`)**：仅当核心玩法或技术底座发生不兼容的颠覆性换代时才允许升级 |

## 二、三类版本号解耦与单一真源原则

严禁将“对外产品版本号”、“存档数据结构版本号”与“CI 构建流水号”混为一谈：

### 1. 产品版本号 `GAME_VERSION`（唯一真源）
- **定义位置**：`05-微信小游戏版本/src/constants.js` 导出 `GAME_VERSION`（如 `'0.9.0'`、`'1.0.0'`）。
- **消费方**：
  - 局内调试契约 `globalThis.__HOSHI_DEBUG__.version` 直接读取 `GAME_VERSION`；
  - 暂停/设置/关于弹窗如需展示版本号，统一读取 `GAME_VERSION`，禁止在其他 `.js` 文件中重复手写。

### 2. 存档结构版本号 `SCHEMA_VERSION`（数据契约）
- **定义位置**：`05-微信小游戏版本/src/save_sync.js` 与云函数 `cloudfunctions/kissa_sync/index.js` 共同维护整数 `SCHEMA_VERSION`（当前为 **`2`**）。
- **升降级铁律**：
  - **禁止随产品版本同步递增**：`v0.8.0 → v0.9.0 → v1.0.0` 若存档结构保持兼容，均继续使用 `SCHEMA_VERSION = 2`；
  - **仅当发生结构性变更**（需要编写 `migrateVxToVy` 迁移函数或重算星尘守恒时）才将 `SCHEMA_VERSION` 递增为 `3`；
  - **高版本防覆盖写保护**：客户端拉取云端存档若发现 `cloudDoc.schemaVersion > SCHEMA_VERSION`，必须触发 `higherSchemaDetected = true` 并禁止覆盖写回云端，提示用户重启更新客户端。

### 3. 微信 CI 自动上传版本号（`miniprogram-ci`）
微信小游戏后台要求上传版本号为纯数字三段式 `MAJOR.MINOR.PATCH`（不带 `v` 前缀或预发布后缀）。
- **日常 CI / 体验版预览（`scripts/upload_minigame.mjs`）**：
  - 当未显式传入 `WECHAT_VERSION` 时，脚本应自动读取 `constants.js` 中的 `GAME_VERSION` 主次版本号 `<MAJOR>.<MINOR>`，拼接 CI 运行号生成 **`<MAJOR>.<MINOR>.<GITHUB_RUN_NUMBER>`**（例如 `0.9.42`），**禁止硬编码 `1.0.<run_number>`**。
- **正式提审版**：
  - 在 GitHub Actions `workflow_dispatch` 手动触发上传时，显式填写标准版本号（如 `1.0.0`、`1.0.1`、`1.1.0`），确保微信后台提交审核的版本号与 `GAME_VERSION`、`CHANGELOG.md` 及 Git Tag 100% 一致。

## 三、文档命名与变更日志规范

1. **长期设计文档不绑死版本号**：
   - 长期演进的主规格书（`docs/00..06` 及 `docs/HANDOVER.md`）**不得使用带版本号的子目录（如 `docs/v2.0/`）或文件名**，始终随当前目标版本就地更新并在文档首部标注当前适用版本。
2. **版本计划书与历史原型归档**：
   - 重大版本调整方案以 `docs/vX.Y.Z-<主题>.md` 命名（如 `docs/v0.9.0-版本调整计划书.md`）；
   - 已淘汰的早期原型文档统一移入 `docs/archive/vX.Y.Z-<名称>.md`，并在顶部注明归档状态。
3. **强制维护 `CHANGELOG.md`**：
   - 仓库根目录 [CHANGELOG.md](../CHANGELOG.md) 采用 Keep a Changelog 格式按时间倒序记录所有版本改动（分为 `Added` / `Changed` / `Fixed` / `Removed`）。

## 四、标准发版 Checklist

每次提升 `GAME_VERSION`（包括未来 `v0.9.0` 落地与 `v1.0.0` 正式首发）必须依次核对以下 5 项：

1. **同步真源**：更新 `05-微信小游戏版本/src/constants.js` 中的 `GAME_VERSION`（若有存档结构变化，同步更新 `SCHEMA_VERSION` 与云函数 `kissa_sync`）。
2. **补全日志**：将 `CHANGELOG.md` 中 `[Unreleased]` 的条目归档至 `[X.Y.Z] - YYYY-MM-DD` 节点下。
3. **全量门禁**：确认 `node --check`、`node scripts/test_v2_core.mjs`（含客户端↔云函数同构断言）与 `node scripts/verify_minigame_e2e.mjs` 100% 全绿，且主包原始体积 `<= 3.5 MB`。
4. **云后端先于客户端发布**：若本版本涉及 `cloudfunctions/kissa_sync/` 数值上限或防刷校验变更，须先在微信开发者工具上传部署云函数，再提交客户端代码审核。
5. **打 Tag 留档**：发版合并 `main` 后创建标准 Git Tag（格式 `vX.Y.Z`，如 `v0.9.0`、`v1.0.0`）。
